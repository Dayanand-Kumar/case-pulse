OPERATIONS GUIDE

Deployment documentation

A step-by-step guide to prepare an Amazon EC2 server, configure PostgreSQL, publish the CasePulse frontend, and keep the API running.

Start at step 1
IN THIS GUIDE 1. Before you start 2. Create the EC2 instance 3. Install software 4. Set up PostgreSQL 5. Create folders and deploy code 6. Configure the application 7. Run the API with systemd 8. Publish the frontend 9. DNS and HTTPS 10. Verify and import data 11. Updates, backup, and support Security checklist
Important security note

CasePulse does not currently provide user sign-in or role-based access. Do not expose it to the public internet with sensitive case data unless access is protected (for example, by a VPN or an authenticated gateway) and your organization has approved that access. Never open PostgreSQL port 5432 or the API port 3000 to the internet.

GET READY

1. Before you start

This guide uses Amazon Linux 2023, one EC2 instance running Nginx, the Node.js API, and local PostgreSQL. Nginx serves the compiled Angular app and forwards /api requests to Node on the same machine.

  • AWS account with permission to create EC2, security groups, DNS records, and (if using HTTPS) an Application Load Balancer and ACM certificate.
  • A Git repository URL that the EC2 instance can access, or an approved way to upload a release archive.
  • A DevOps CSV/XLSX workbook with the exact headers documented in the app's import flow.
  • A domain name if you want a stable public URL and HTTPS.
Traffic flowBrowser HTTPS gateway / Nginx Angular static filesBrowser Nginx /api proxy Node.js API PostgreSQL on localhost
AWS CONSOLE

2. Create and secure the EC2 instance

  1. In AWS Console, open EC2 Launch instance. Choose Amazon Linux 2023 (64-bit x86) and a size approved for your expected data and traffic; a small instance is suitable only for a trial.
  2. Create or select a key pair and keep the private key somewhere secure on your workstation. Do not upload it to the source repository or EC2 application folder.
  3. Place the instance in the network/subnet approved for your organization. Allocate an Elastic IP if you need a stable address without a load balancer.
  4. Create a security group with inbound SSH (TCP 22) restricted to your current trusted IP/CIDR only. For direct Nginx access, allow HTTP (TCP 80) and HTTPS (TCP 443) only from the intended clients. If using an ALB, allow 80/443 from the ALB security group instead. Do not add inbound rules for 3000 or 5432.
  5. Launch the instance and note its public DNS name or Elastic IP.

From Windows PowerShell, connect using your downloaded key (replace the sample path and host):

ssh -i "$HOME\Downloads\casepulse-ec2.pem" ec2-user@YOUR_EC2_PUBLIC_DNS
ON EC2 AS ec2-user

3. Install the required software

Update packages, then install Node.js 22 (supported by this Angular project), npm, Git, Nginx, and PostgreSQL 15:

sudo dnf update -y
sudo dnf install -y nodejs22 nodejs22-npm git nginx postgresql15 postgresql15-server
node --version
npm --version
psql --version
nginx -v

Amazon Linux names the Node 22 packages nodejs22 and nodejs22-npm. Confirm the active version is supported by the Angular CLI before building.

ON EC2 POSTGRESQL

4. Initialize PostgreSQL and create the app database

Initialize the database cluster once, then start PostgreSQL now and on boot:

sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql
sudo systemctl status postgresql --no-pager

Create a dedicated database owner. Enter the interactive PostgreSQL prompt first:

sudo -u postgres psql

At the postgres=# prompt, run these SQL/psql commands. Choose a strong unique password when prompted by \password; do not put it in shell history.

CREATE ROLE casepulse_app LOGIN;
\password casepulse_app
CREATE DATABASE casepulse OWNER casepulse_app;
\q

The API runs the project's backend/schema.sql migration when it first connects. That migration creates the DevOps_SF_Summary schema and required tables (including case and risk data, resources, and team activities). Do not manually create alternate workbook columns.

ON EC2 APPLICATION FILES

5. Create the folders and deploy the code

Use one owned directory for the checkout and generated frontend files. The confidential .env stays in the app directory, is never committed, and must be readable only by the service account.

/opt/casepulse/
 app/
     backend/
        server.js
        schema.sql
     dist/
        case-pulse/
            browser/       # generated by npm run build
     src/                   # frontend source
     package.json
     package-lock.json
     .env                   # secrets; never commit or publish

Create the parent folder and transfer ownership to the standard EC2 account:

sudo mkdir -p /opt/casepulse
sudo chown ec2-user:ec2-user /opt/casepulse

Clone your authorized repository (replace the placeholder with your repository URL):

git clone YOUR_GIT_REPOSITORY_URL /opt/casepulse/app
cd /opt/casepulse/app
npm ci
npm run build

For a private repository, configure approved read-only Git access for this instance; do not paste access tokens into the clone URL or commit them. Confirm the static output exists:

ls -la /opt/casepulse/app/dist/case-pulse/browser
ON EC2 PRIVATE CONFIGURATION

6. Configure the environment

Copy the template and edit the production values. Use nano or your approved editor; replace placeholders and save:

cd /opt/casepulse/app
cp .env.example .env
nano .env

Set at least these values (use the database password created in step 4 and your real browser origin):

API_PORT=3000
PGHOST=127.0.0.1
PGPORT=5432
PGDATABASE=casepulse
PGUSER=casepulse_app
PGPASSWORD=REPLACE_WITH_YOUR_STRONG_DATABASE_PASSWORD
PGSSL=false
PGSCHEMA=DevOps_SF_Summary
CORS_ORIGIN=https://YOUR_APP_DOMAIN

For temporary testing over HTTP, use http://YOUR_EC2_PUBLIC_DNS as the origin and change it to the final HTTPS origin when configured. Keep PostgreSQL bound to localhost. Lock down the file and verify ownership:

chmod 600 /opt/casepulse/app/.env
chown ec2-user:ec2-user /opt/casepulse/app/.env

Do not paste the real password into chat, documentation, Git, or diagnostic output. Do not enable PGSSL for local loopback PostgreSQL; use verified TLS settings if the database is remote.

ON EC2 START ON BOOT

7. Run the Node API as a systemd service

Create a service file:

sudo nano /etc/systemd/system/casepulse-api.service

Paste this unit, then save:

[Unit]
Description=CasePulse Node.js API
After=network.target postgresql.service
Requires=postgresql.service

[Service]
Type=simple
User=ec2-user
WorkingDirectory=/opt/casepulse/app
Environment=NODE_ENV=production
ExecStart=/usr/bin/node /opt/casepulse/app/backend/server.js
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Enable and start it, then check the service and API health endpoint. The health check also triggers the schema migration:

sudo systemctl daemon-reload
sudo systemctl enable --now casepulse-api
sudo systemctl status casepulse-api --no-pager
curl -i http://127.0.0.1:3000/api/health

Expect an HTTP 200 response indicating the database connection is healthy. If not, inspect logs with sudo journalctl -u casepulse-api -n 100 --no-pager and resolve the database/configuration error before proceeding.

ON EC2 WEB SERVER

8. Publish Angular with Nginx

Create a site configuration:

sudo nano /etc/nginx/conf.d/casepulse.conf

Paste the following configuration. Replace the server name with your DNS name, or use the instance public DNS for a smoke test:

server {{ '{' }}
    listen 80;
    server_name YOUR_APP_DOMAIN;
    root /opt/casepulse/app/dist/case-pulse/browser;
    index index.html;

    location /api/ {{ '{' }}
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    {{ '}' }}

    location / {{ '{' }}
        try_files $uri $uri/ /index.html;
    {{ '}' }}
{{ '}' }}

Validate the configuration and enable Nginx:

sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx

The SPA fallback serves Angular routes; the API proxy keeps port 3000 private. If Nginx cannot read the build files, check directory execute permissions and file read permissions along /opt/casepulse/app/dist.

AWS CONSOLE PRODUCTION ACCESS

9. Point DNS and enable HTTPS

  1. Create a DNS record for your app domain pointing to the Elastic IP, or create an Application Load Balancer and point DNS to its name.
  2. For production, terminate HTTPS with an Application Load Balancer and an ACM certificate for your domain. Validate the certificate, configure an HTTPS listener on port 443 to forward to the instance target group on port 80, and enable an HTTP-to-HTTPS redirect.
  3. Restrict the EC2 security group so web traffic to port 80 comes only from the ALB security group; keep SSH restricted to trusted administrator IPs. Do not expose the API or database ports.
  4. Update CORS_ORIGIN in .env to the exact public HTTPS origin, then run sudo systemctl restart casepulse-api.
  5. Open the HTTPS domain and confirm the browser shows a valid certificate. HTTP-only access is suitable for a short private smoke test, not for a public production deployment.
SMOKE TEST

10. Verify the deployment and load data

  1. From EC2, verify curl -i http://127.0.0.1:3000/api/health returns HTTP 200 and a connected database.
  2. Verify Nginx responds with the app: curl -I http://127.0.0.1/. Then open the public HTTPS address in a browser.
  3. Check the PostgreSQL status badge in the left sidebar. If disconnected, inspect both the API and PostgreSQL service logs.
  4. Import the approved case workbook in the Salesforce Case Tracker. Use the Risks toggle to import Risk Summary rows to their separate table. The case workbook must have the exact 14 headers and order; Risk Summary uses its exact 10 headers and order.
  5. Apply filters, open Dashboard and Team workload, and test XLSX export. Confirm that records remain after refreshing the page.

Keep the workbook headers and order unchanged. Importing or exporting different column layouts can cause validation failures; the risk-summary schema migration can recreate a mismatched risk table and remove its rows.

OPERATIONS

11. Updates, backups, and useful commands

Deploy an update

Run as ec2-user after reviewing the release and any database migration:

cd /opt/casepulse/app
git pull --ff-only
npm ci
npm run build
sudo systemctl restart casepulse-api
sudo nginx -t
sudo systemctl reload nginx
curl -i http://127.0.0.1:3000/api/health

Back up PostgreSQL

Use an approved secure backup destination and retention policy. The following writes a database dump to a protected local folder; copy it off-instance using your approved encrypted backup process:

sudo install -d -m 700 -o ec2-user -g ec2-user /opt/casepulse/backups
nano /home/ec2-user/.pgpass
chmod 600 /home/ec2-user/.pgpass
export PGPASSFILE=/home/ec2-user/.pgpass
pg_dump -h 127.0.0.1 -U casepulse_app -Fc casepulse -f /opt/casepulse/backups/casepulse-$(date +%F).dump

Put the database credentials in the protected password file using the format 127.0.0.1:5432:casepulse:casepulse_app:YOUR_DATABASE_PASSWORD. Do not put a real password in the command or shell history. Prefer an approved secrets manager for scheduled backups. Test restoring a backup into a separate database before relying on it.

Service status and logs

sudo systemctl status casepulse-api nginx postgresql --no-pager
sudo journalctl -u casepulse-api -n 100 --no-pager
sudo tail -n 100 /var/log/nginx/error.log
Production change control

Before updating dependencies or schema, take a database backup, review the change, deploy to a test environment where possible, then verify health and workbook import/export after release.

FINAL CHECK

Security checklist

  • Restrict SSH to trusted administrator addresses; use key-based access and rotate/revoke access when needed.
  • Do not allow inbound internet access to TCP 3000 or 5432. Bind PostgreSQL to loopback for this single-instance deployment.
  • Use HTTPS and an authenticated access boundary before storing or displaying real case data; the application itself has no login.
  • Keep .env, private keys, database dumps, and repository credentials out of Git, the web root, and public logs. Restrict file permissions.
  • Apply OS and dependency updates, monitor disk space and service health, and maintain tested encrypted backups off the instance.
  • Grant the database role only the permissions needed by the API. Review AWS IAM role permissions and avoid long-lived cloud keys on the instance.
